# Live-Data Findings — sms-teacher-app (2026-07-24)

Classification: (a) app-side wiring gap · (b) backend gap · (c) acceptable derived value

## Summary

- Total findings: 116
- (a) App-side wiring gaps: 25
- (b) Backend gaps: 32
- (c) Acceptable derived values: 59

### Backend gaps requiring sms-backend changes (priority order)

1. **`GET /auth/me` missing user/tenant fields (`name`, `title`, `tenant_name`, `joined`, `email`, `phone`, `classroom`, `employee`, `must_set_password`)** — `AuthService.GetMe` returns only `{ id, tenant_id, roles, is_platform }`; no user "name" concept exists anywhere in the backend user model (`UserModels.cs`/`IAuthDao`). This single root cause blanks or fakes identity/profile data across `SetPasswordScreen` (gating + greeting), `ProfileScreen` (initials, name, title, tenant name, joined, email, phone, classroom, employee ID), `HomeScreen` (first name, tenant name, initials), and `PrincipalHomeScreen` (greeting name, title, initials). It also permanently blocks the first-time-password gate from ever firing against live data. **17 rows.** (Note: `AnnouncementsScreen`'s "From" field also falls back to a role string, but that is a *separate* root cause — see item 3 below. Adding fields to `/auth/me` would not fix it: the announcement "From" gap needs a creator-name resolved via `GET /announcements`, not the auth-session endpoint.) Highest priority: touches nearly every screen and blocks a whole auth flow. Possible cheaper fix path: `dbo.Teachers.Name` (see item 3's note) is a real, already-populated staff-directory column used today by `/principal/overview` and `TeacherDirectoryScreen` — `GetMe` may be able to join to it for `name`/`title` rather than requiring an entirely new "name" concept, which would reduce the effort estimate for this item.
2. **`GET /timetable` has no teacher/user filter** — `TimetableRepository.ListAsync` runs an unfiltered `SELECT` over all of `dbo.TimetableSlots`, and the table has no `TeacherId`/`UserId` column to filter by. Every signed-in teacher receives the entire tenant's timetable. **1 row**, but flagged as high priority ahead of higher-row-count items because it is a cross-tenant/whole-school data-exposure issue, not just a missing display value.
3. **Creator/requester display-name resolution is missing on two endpoints: `GET /approvals` (`LeaveResponse`) and `GET /announcements` (`AnnouncementResponse`)** — `LeaveResponse` carries only a bare `RequesterId` Guid with no join to a staff/user directory, so every approval card shows the hardcoded `'Staff member'`/`'—'` placeholders regardless of who applied (affects `ApprovalsScreen` and its reuse on `PrincipalHomeScreen`); separately, `AnnouncementController.Create`/`AnnouncementService.CreateAsync` only ever pass the creator's *role* string (never a name) into `From`, so `AnnouncementsScreen`'s "From" meta always renders a role label instead of the sender's real name. These are the same *category* of gap (missing creator/requester display-name resolution) on two different endpoints — not a single shared root cause with `/auth/me` (item 1); fixing `/auth/me` would not fix either of these. **3 rows** (2 approvals-reuse rows + 1 announcements row). Trust/accountability issue for an approve-or-reject workflow, and for attributing announcements to their real author. Possible cheaper fix path: both gaps may be resolvable via a join to the existing, already-populated `dbo.Teachers` staff-directory table (confirmed real and populated — see the `PrincipalHomeScreen`/`TeacherDirectoryScreen` `dbo.Teachers.Name` finding in the table below) rather than requiring a brand-new name/identity concept — this should reduce the effort estimate for whoever plans Phase 3.
4. **`GET /classes`'s `student_count` is a stubbed-always-0 column** — `Class_Create.sql`/`Class_Update.sql` never write a real value; `ClassRepository.ListAsync` selects it as-is off `dbo.Classes` (default `0` from `M0015_Academics_Tables.cs`). Every class card/section badge on `HomeScreen`, `AttendancePickClassScreen`, and `ClassesScreen` renders "0 students". **3 rows.**
5. **`dbo.Students.AttendancePct` is a stubbed-always-0 column** — selected by `StudentRepository` but never written by `Student_Create.sql`/`Student_Update.sql`. Every per-student attendance badge on `ClassDetailScreen` and `StudentScreen` renders "0%"/"Absent"-tier regardless of real history. **2 rows.** (Distinct root cause from item 4 above — different table/column, do not conflate.)
6. **`ExamPaperResponse` has no `topics` field** — no topics/syllabus-coverage concept exists anywhere on the backend (zero matches for "Topics" in `sms-backend/src`). `ExamDetailScreen`'s "Topics Covered" is always empty, and `ExamNewScreen` silently discards whatever topics a teacher types since there's nowhere to persist them. **2 rows.**
7. **`ClassResponse` has no `next_period` field** — not even a stubbed column; the field doesn't exist on the backend at all. `ClassesScreen`'s "next period" pill can never render. **1 row.**
8. **`GET /bus/{busId}/position`'s `EtaMinutes` is hardcoded to `null`** — no ETA calculation exists in the backend, and the app's non-nullable zod-less field casts the null straight through, so `BusScreen` literally renders "~null min". **1 row.**
9. **`LeaveResponse` has no `priority`/urgency field** — no urgency concept exists for leave requests anywhere in the backend; `ApprovalsScreen`'s priority dot is hardcoded to "medium" for every request. **1 row.**
10. **`ChatThreadResponse` has no online/presence field** — no presence/last-seen mechanism exists on the backend; the app's "online" dot is hardcoded `false`. **1 row.** Lowest priority: cosmetic, no misleading data implication (never claims a contact is online when they aren't).
11. **No backend endpoint exists for persisting user notification/display preferences** — `SettingsScreen`'s entire toggle set (Push Notifications, Email Alerts, SMS Alerts, Attendance Reminders, Dark Mode, Font Size, Language, Two-Factor Authentication, Biometric Login) has no corresponding `GET`/`PUT` endpoint anywhere in `sms-backend` to read or persist real values — no settings/preferences table or controller was found. This is a buried (b) component of the `SettingsScreen` row below, which is classified purely (a) because the row's *primary* observation is that the app never even attempts to call a backend for these values; but even if the app were wired to try, there is currently nowhere on the backend to read from or write to. Listed here for completeness, consistent with how other compound (a)+(b) gaps in this audit are called out (e.g. the `ExamNewScreen` topics-field finding) — this does not change the row-level classification counts above (still 25 a / 32 b / 59 c), since only one table row exists for this finding.
