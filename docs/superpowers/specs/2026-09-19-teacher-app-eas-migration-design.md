# Teacher App EAS Migration — Design

## Goal

Make `D:\SMS\sms-project\teacher-app` a real, runnable copy of the production
Teacher app (`sms-teacher-app`), linked to a separate Expo/EAS account
(`vaibhavdds-team`, project `8520504e-1cdf-41a1-9cbb-56cd896e6763`), installable
on a physical Android phone for QA — without touching or downgrading the real
`sms-teacher-app` project.

## Non-goals

- No migration to Expo Router or Expo SDK 57. `teacher-app` inherits
  `sms-teacher-app`'s SDK 54 / RN 0.81.5 / React Navigation stack as-is.
- No UI redesign, no new features, no architecture changes.
- No changes to `sms-teacher-app` itself — it remains the source of truth and
  is not deleted or modified.
- No production/staging config changes to carry the LAN IP.

## Approach: source replacement, not code porting

Delete the SDK 57 / expo-router scaffold contents of `teacher-app` and replace
them with a direct copy of `sms-teacher-app`'s source tree (`src/`, `assets/`,
config files, etc.), then re-identify the copy for the new EAS account. This
avoids any rewrite risk — the copied code is byte-identical to the working app
except for identity/config fields below.

## Backend configuration

- Local `.env` in `teacher-app` (gitignored, never committed):
  ```
  EXPO_PUBLIC_API_BASE_URL=http://192.168.29.149:5162/v1
  ```
  Used only for `npx expo start --dev-client` + phone on the same LAN.
- `eas.json` `development` and `preview` build profiles keep pointing at the
  existing staging URL (`https://staging-api.schooldesk.app/v1`) — this is the
  reliable path that needs no network setup and survives network changes.
  The LAN IP is never written into `eas.json` or any committed file.
- Before relying on LAN mode: verify Windows Firewall allows inbound TCP 5162,
  and that the ASP.NET backend is bound to `0.0.0.0`/the LAN interface, not
  only `127.0.0.1`/`localhost`.

## Authentication audit (must happen before any code is assumed safe)

Audit `sms-teacher-app`'s actual auth implementation for:

- Refresh-token storage and rotation
- Token/session revocation behavior
- Any device or session identifier tied to login
- Logout behavior (does logout revoke only the current session, or all
  sessions for the account?)

Do not assume JWT implies multi-device support. Report findings plainly:
if the backend already supports independent concurrent sessions per device,
preserve that behavior unmodified. If a single-device lock is found, report
it as a blocker rather than silently changing auth logic.

## Migration steps (detail for implementation plan)

1. Audit both projects' full config (already partially done — SDK/RN
   versions, `app.config.js`, `eas.json`, android/ios config, entry point,
   navigation, auth, API layer, env vars, assets, fonts, notifications,
   storage, permissions, deep links, native modules).
2. Audit auth/session code specifically (see above).
3. Copy `sms-teacher-app` source into `teacher-app`, excluding
   `node_modules/`, `.expo/`, `.git/`, build artifacts, and the real app's
   `.env` (secrets stay out).
4. Apply identity changes from the table above in `teacher-app/app.config.js`.
5. Create `teacher-app/.env` with the LAN API URL (gitignored).
6. Verify `teacher-app/eas.json` profiles use staging URL, matching
   `sms-teacher-app`'s existing profiles.
7. `npm install` in `teacher-app`.
8. Run `npx tsc --noEmit`, existing lint/test suite, `npx expo start
--dev-client` sanity check.
9. `eas build --profile development --platform android` for a real device
   build.
10. Multi-device acceptance testing (below).
11. Git: review diff, commit `teacher-app` (no secrets/`.env`), leaving
    `sms-teacher-app` untouched.

## Acceptance testing — mandatory before declaring complete

Install the development build APK on two physical Android devices (Mobile A,
Mobile B), log in with the same teacher account on both, against the same
staging backend, and verify:

1. Mobile A login
2. Mobile B same-account login
3. Simultaneous sessions (A and B both stay authenticated; login on B does not
   log A out)
4. Mobile B offline — shows previously cached data
5. Mobile A makes a supported data change while online
6. Mobile B reconnects — verify sync/refresh behavior
7. Mobile A logout — verify Mobile B's behavior matches the backend's actual
   session policy (not assumed)
8. No cross-account/tenant data leakage between devices

Each device keeps its own independent local cache — no assumption that cache
is shared between devices.

## Final report format (exact)

```text
Mobile A login: PASS/FAIL
Mobile B same-account login: PASS/FAIL
Simultaneous sessions: PASS/FAIL
Offline Mobile B: PASS/FAIL
Reconnection/sync: PASS/FAIL
Cross-device data refresh: PASS/FAIL
Logout/session behavior: PASS/FAIL
LAN backend connectivity: PASS/FAIL
Account/tenant data isolation: PASS/FAIL
```

Plus: Expo SDK/version, EAS project ID, Android package id, Expo Go
compatibility (expected: no, due to native modules — dev build required),
exact run/build commands, backend URL used for device testing, any remaining
blockers, git status and commit hash.
